# M4 媒体与同步

状态：当前 v1 全量快照同步已接入；v2 设计有条件通过，表和部分媒体函数已建立，尚未实现端到端协议。

## 衣物到底放在哪里

衣物元数据和图片都需要本机副本，供离线使用；登录并成功同步后，服务器保存可恢复副本。数据库保存名称、类别、关系、图片归属和引用，图片文件放服务端私有目录，不放公开静态资源目录。

当前本机 IndexedDB 保存含 base64 图片的快照，服务器将快照中的图片提取到 `DATA_DIR/media/<账号哈希>/<图片哈希>`。账号哈希是路径组织方式，不代替鉴权。相同图片在不同账号下各自归属，不能凭哈希跨账号读取。

本地演示、未登录或同步失败时，最新内容可能只有本机副本。卸载前应检查同步/备份状态，不能把界面“已保存”理解成“云端已有备份”。

## 当前 v1 限制

- `/api/state/pull`、`push` 传输完整状态及图片；`expectedVersion` 比较整个账号版本。
- 冲突需要选择整份本机或云端状态，覆盖前在本机备份。
- 单张图片上限 3 MiB，状态请求上限 30 MiB；媒体配额默认 200 MiB。后两项不等价，现有传输无法装满账号容量。
- 本机快照重复携带图片，备份导入限制 30 MiB；原生导出还有独立长度上限。
- `media.js` 的回收逻辑尚未接入运行路径，不能承诺删除衣物后已自动释放服务器空间。

## v2 目标协议（待实现）

实体按账号、类型和 ID 定位：衣物、穿搭、模特、试穿记录、收藏成员、设置。图片先单独上传并得到 `media:<sha256>`，实体只传引用。

每条实体有独立 version 和 deleted 墓碑。变更日志提供服务端 cursor；一次实体修改、版本增加、日志写入和 mutation 回执同事务提交。

推送以稳定 mutationId 和 expectedVersion 实现重试去重；同 ID 换请求体拒绝。确认的是“已发送版本”，不能清掉网络期间产生的新修改。推送回执不能推进拉取游标。

拉取按稳定边界分页，客户端在同一个 IndexedDB 事务保存实体、基线、冲突和游标。不同衣物的离线修改可合并；同一实体冲突由用户逐条选择。删除与编辑冲突不能自动复活记录。

## 媒体与回收目标

图片按真实字节计算 SHA-256，验证内容、大小、账号归属；配额检查和登记串行化。落盘成功后才能接受实体引用。客户端 Blob 缓存按服务与账号分区，按可见内容下载，不能启动时拉完整图库。

回收扫描当前实体和有效任务输入/结果，至少保留 24 小时上传宽限；重新上传要刷新宽限。回收与新引用写入共用事务边界。历史变更的图片引用必须与拉取语义一致，不能向客户端下发已回收的图片。

旧快照迁移完成后不能继续永久占用媒体；短期 AI 输入和长期用户记录使用不同保留期。清理磁盘孤立文件需有单独验证，不把数据库行删除等同于磁盘已清理。

## 迁移与备份目标

服务端一次性迁移：读取旧状态 → 建立实体和变更 → 写 migration marker，同事务提交；可重复执行，不丢 ID。旧写接口在迁移后明确拒绝，防止旧 App 覆盖新数据。

客户端在完整提交之前保留旧 data URL 快照。`dataVersion` 是业务结构，`syncVersion` 是传输协议，SQLite `user_version` 是表结构，三者分开管理。

新备份使用 manifest 与媒体清单，验证图片哈希、数量和缺失项；实际验收必须包含超过 30 MiB 的图库。失败不能显示“完整导出成功”。导入不包含令牌，替换前保留可恢复副本。

## 验收用例

分页期间有并发写入、确认回执丢失、推送期间继续编辑、删除与编辑冲突、重复迁移、媒体配额竞争、回收与新引用竞争、图片缺失、磁盘写入失败、大文件备份、跨账号延迟响应、注销时有在途任务。
